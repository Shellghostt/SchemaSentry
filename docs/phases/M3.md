## Scope and boundaries

Implement the internal classification registry, SS001–SS007, explicit rename hints and minimal SQL
evidence parsing needed by SS005/SS007. Parse migration files as data; never execute user SQL.
Risk aggregation/modifiers, public reports, thresholds, `compare` and `explain` remain M4.
GitHub Action integration and broader parser integration remain M5; MySQL remains M6.
M2 `diff` must continue producing its current structural JSON and exit 0 even when changes exist.
Do not attach classifications to that response or activate threshold exit codes as an incidental change.

## Rule accuracy contract

| Rule | Classification evidence and limitations |
|---|---|
| SS001 | An actual removed column. A validated rename hint prevents a false data-loss classification. Removal breaks readers that still reference the column; do not claim every reader does. |
| SS002 | Before/after types, typmods and PostgreSQL version. Preserve the plan's severity matrix, but keep cast/rewrite claims conditional on known server semantics. Unknown types/casts are unsupported or low-confidence, not safe. |
| SS003 | Adding NOT NULL may require checking existing rows whether or not a default exists. A default does not prove historical rows satisfy the constraint. A known validated CHECK may permit scan avoidance; NOT NULL still needs its DDL lock. |
| SS004 | Foreign-key referencing columns lacking a usable supporting index. PostgreSQL does not auto-create that index. Define index validity, key-prefix order, expressions and partial predicates; an unusable/unknown candidate cannot establish coverage. |
| SS005 | Parse operation evidence for locking/rewriting statements, including ALTER TABLE type/nullability/default changes and VACUUM FULL. Separate lock acquisition from scan/rewrite; snapshot differences alone cannot prove how a migration was executed. |
| SS006 | Explicit, validated one-to-one column rename hints. Reject missing endpoints, collisions, cycles or ambiguous mappings. Without hints retain drop/add; preserve M2's existing index/constraint rename suppression. |
| SS007 | Known volatile default versus non-volatile expression versus unknown function volatility, with PostgreSQL version. A nonliteral expression is not automatically volatile or rewriting. Unknown user functions need explicit uncertainty. |

For PostgreSQL 11+ a non-volatile ADD COLUMN default can use the fast-default path rather than rewrite
the table; volatile defaults can require rewriting. This says nothing about safety of arbitrary casts,
generated columns or other DDL. Do not promise durations from syntax alone.

`NOT VALID` applies to CHECK/foreign-key constraints, not directly to NOT NULL. An SS003 alternative may
use a CHECK `(column IS NOT NULL) NOT VALID`, validate it, then SET NOT NULL where the supported version
can use the proof. Document each step's locks and concurrent-write behavior; this is not lock-free DDL.

Type-matrix entries such as int-to-bigint and numeric widening retain their specified base severity,
but actual conversion effects depend on version, typmods and USING expressions. Increasing varchar
length is a distinct case from arbitrary casts. Add version-specific corpus evidence before claiming
no rewrite or scan. SS008–SS010 belong to M4 and remain outside this phase.

## Evidence and parser contract

- Classifications carry stable rule/object identity, base severity, evidence, confidence and limitations.
  No fabricated row estimates, original migration intent, lock durations or user-function volatility.
- Define a bounded parser result with statement order, supported operation, source location and explicit
  unsupported/parse-error entries. Multi-statement files, quoted/schema-qualified identifiers, comments,
  USING clauses and transaction wrappers need fixtures. SQLGlot acceptance is not proof of PG semantics.
- Unsupported syntax or absent migration evidence must be visible to the caller/corpus; never silently
  mark the migration safe. M3 can test this through internal results without adding an M4 CLI report.
- Validate hint files as data with a bounded versioned shape. Apply matching independently of input
  ordering, without mutating snapshots or changing existing structural-diff behavior.
- Keep captured scope limitations: sequences, extensions and uncaptured table properties are outside
  M2 structural comparison. Do not broaden these silently while adding classification.

## Decisions to record before implementation

Write an M3 ADR for the internal finding/parser/hint contracts, SS003/SS007 corrections and server-version
evidence. Move the minimal parser dependency ahead of SS005 in the backlog; full CI integration stays M5.
Accepted ADRs stay unchanged. Retain PG 13/15/16 compatibility regression tests unless a separate
support decision changes them. PG13 compatibility coverage is not a deployment recommendation; it is
upstream unsupported. State the tested server versions rather than claiming all PostgreSQL versions.

## Acceptance and evidence

- [ ] At least 21 corpus cases: positive, negative and edge for each SS001–SS007; extra cases cover ambiguity.
- [ ] SS002's matrix and version/cast caveats pass, without inferred safe conversions.
- [ ] SS003 tests defaults, pre-existing nulls and validated-CHECK evidence; SS007 tests unknown functions.
- [ ] SS004 rejects invalid/partial/expression indexes when they do not establish FK coverage.
- [ ] Hint validation and shuffled-input cases preserve deterministic classification and existing renames.
- [ ] Supported/unsupported SQL and parse failures are visible; migration content is never executed.
- [ ] Existing M2 structural JSON, CLI exits, snapshots and live PG compatibility tests still pass.
- [ ] Corpus completes under 60 seconds; `make test`, `make lint`, `make type` and CI pass with evidence.

Use [M1/M2 validation](../testing/m1-m2-validation.md) for infrastructure and existing checks.
M3 corpus execution may apply synthetic fixture SQL only to isolated test databases, never to a user's
database. Log commands, server versions, case counts, elapsed time and skips in an M3 validation record.
These are future gates; this documentation pass does not establish classifier accuracy.
