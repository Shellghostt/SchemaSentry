## Scope and preserved contracts

Implement SS-020A and SS-021–SS-025: SS008–SS010, deterministic risk aggregation, Markdown/JSON reports,
threshold exits, public `compare`, offline `explain`/`rules`, and corpus expansion. CLI wiring belongs
explicitly to SS-023/SS-024. GitHub Action/comment publication and broader migration-directory parsing
remain M5; MySQL and calibrated runtime analysis remain M6.

Preserve M2 structural `diff`: same JSON schema/ordering, same changes/warnings and success exit 0 even
when changes exist. Do not attach risk findings or turn on threshold exits in that command incidentally.
Keep read-only REPEATABLE READ capture, five-second statement timeout, strict snapshot loading and
M3 immutable classification/evidence/rename-hint semantics. SQL/hints remain bounded data, never commands.

M3 supports SS001–SS007 internally and has 59 reviewed cases. PostgreSQL capture accepts majors 13–17;
confirmed version-specific classification effects are backed by PG13/15/16 tests. Other versions and
uncaptured table/inheritance properties remain uncertain until evidence/support is deliberately expanded.

## New rule accuracy

| Rule | Required evidence and boundaries |
|---|---|
| SS008 | Identify the actual supported added CHECK/FK constraint and whether validation was requested. `NOT VALID` applies to supported CHECK/FK constraints, not UNIQUE, PRIMARY KEY or NOT NULL. Snapshot absence of validation metadata is unknown; a parsed operation alone is not proof it executed. |
| SS009 | Identify a supported index creation and its concurrency/transaction context. Ordinary builds block writes; `CONCURRENTLY` has extra work, can fail leaving an invalid index and cannot run inside an explicit transaction block. It is not a universal lock-free alternative; partition/version restrictions need explicit evidence. |
| SS010 | Use known enum membership/rename/recreation evidence and dependent objects. PostgreSQL supports enum value rename but has no direct `DROP VALUE`. Column type strings do not supply label membership. Removal/rebuild/data mapping advice is conditional and can affect applications. |

Extend typed catalog/parser evidence only where necessary for these rules. Resolve enum representation
and snapshot compatibility before changing capture/schema models; missing legacy enum evidence cannot
be interpreted as an empty enum. Preserve quoted identifiers, explicit default-schema binding, source
locations, transaction wrappers and unsupported/parse-error notices. Add positive, negative, edge and
unknown-evidence cases before implementation, with PostgreSQL references in each rule page/corpus note.

## Scoring contract to settle before code

The old PLAN mixes `max()` with additive level bumps and counts foreign-key exposure twice. An accepted
scoring ADR must define one formula, cap, deduplication and threshold policy. Proposed ADR 0005 recommends
ordinal `low < medium < high < critical`, additive distinct known modifiers capped at critical, and
overall risk equal to the highest scored finding. It is a recommendation, not implemented behavior.

- Retain base severity separately from final risk. Confidence and evidence limitations are separate;
  low confidence must not silently lower severity or become proof of safety.
- Size tiers use strict boundaries: no size bump at 1,000,000; +1 above 1,000,000 through 20,000,000;
  +2 above 20,000,000. Do not add both size tiers. Test below/at/above each boundary and missing statistics.
- An incoming-FK exposure modifier needs known relevant constraints and a precise count/distinctness
  definition. A unique constraint is not an extra implicit bump. Missing/legacy metadata stays unknown.
- The service-reader lock modifier requires ownership evidence that JSON rename-hints v1 does not carry.
  Do not infer readers from names or invent hints-v2 support. Leave it unavailable in M4 unless a separate
  accepted compatible evidence extension explicitly adds it.
- `rowEstimate` is a catalog estimate, not an exact row count. `estimatedSeconds` stays null without a
  supported rewrite, relevant size evidence and a measured, documented estimation model. Row count alone
  cannot produce seconds. No calibrated timing model is delivered by this preparation or required in M4.

## Public CLI and report contract

Use a new `compare` flow rather than changing `diff`. The recommended shape is `--baseline FILE` with
either an explicit after-snapshot or a read-only database capture. Optional single migration/hint files
reuse current bounds; broader migration-directory traversal remains M5. If a database is captured, the
report compares the schema actually observed there. It does not predict the future schema from SQL or
apply the supplied migration. State that limitation in help/examples before calling this a CI gate.

Define the final flags, environment precedence and defaults in ADR 0005 before implementation. An offline
after-snapshot choice must not connect because a DSN happens to be set. `explain` and `rules` use registry
metadata with no database/collector activity, including with a database URL in the environment.

Commit a separate public report schema/version. JSON/Markdown derive from one result with stable order,
input/capture version evidence, base/final risk, applied/unknown modifiers, confidence, effects,
limitations, source locations, alternatives and explicit unsupported notices. No current-clock timestamp,
random ID, filesystem iteration order, DSN or secret-bearing traceback may affect the report.
Identical validated inputs/policy yield identical UTF-8/LF bytes; Markdown must escape hostile identifiers,
SQL, pipes, HTML, links and fence sequences. Missing alternatives/durations are null or explicitly unavailable.

Preserve the public meanings in PLAN section 8:

| Exit | M4 rule |
|---|---|
| 0 | Complete analysis with no finding at/above the selected threshold; this does not mean safe |
| 1 | Complete report crosses the selected threshold, without critical risk |
| 2 | Complete report contains critical/blocking risk, regardless of the threshold |
| 3 | Tool/input/parse failure or incomplete required analysis; never a silently clean result |
| 4 | Invalid usage or policy arguments |

Resolve completeness and error precedence explicitly. A supported subset can be reported with notices,
but unsupported target effects must not become a successful complete assessment. Default threshold is
high. Test every threshold, no findings, low-confidence findings, critical precedence, parser failures,
unsupported evidence, invalid flags and output failure through real CLI subprocesses.

Keep existing input bounds: snapshots 64 MiB, one migration 256 KiB/128 statements/20,000 tokens/64 levels,
rename hints 64 KiB/128 mappings. Set report count/byte/resource bounds in the accepted design; fail
explicitly rather than truncate high-risk findings or emit a partial JSON success document.

## Acceptance and future evidence

  coverage, with reviewed expected findings committed before rule code.
- [ ] Preserve all 59 M3 cases; add at least nine new rule cases (at least 68 total), exceeding the original
  60-case floor. The full corpus still completes under 60 seconds with hardware/method recorded.
- [ ] Scoring is deterministic, capped and explained; exact size/FK boundaries, unknown metadata,
  modifier deduplication, confidence and aggregate/critical precedence have focused unit tests.
- [ ] `estimatedSeconds` is null without all required measured evidence; no fabricated timing or safety
  claim appears in JSON, Markdown, rule explanations or CLI help.
- [ ] Public JSON validates against its committed schema and repeated/shuffled-input reports are byte
  identical; Markdown goldens cover malicious identifiers/SQL and preserve all uncertainty/alternatives.
- [ ] Real subprocess tests cover all thresholds and exits 0/1/2/3/4, incomplete analysis, usage/output
  errors, environment precedence and offline metadata commands with collectors/connections disabled.
- [ ] `compare` observes the declared before/after states without executing SQL or predicting an after
  snapshot; M2 structural `diff` bytes/exits and current snapshot/hint contracts remain unchanged.
- [ ] Any enum/schema evidence extension has explicit compatibility, legacy-unknown and read-only
  catalog tests on supported PostgreSQL versions; unsupported syntax/version cases stay visible.
- [ ] Report/input resource bounds pass at/over-limit tests and representative 500-table workloads stay
  within the existing snapshot/diff/memory budgets.
- [ ] Canonical Python test/lint/type/build/audit gates and final Python/PG CI matrices pass; skips are named.
- [ ] The eventual M4 validation record maps every criterion to actual test names, commands and limitations.
