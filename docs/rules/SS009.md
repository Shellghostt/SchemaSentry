# SS009: Index creation blocks writes

Generated by `make docs` from the public registry; edit registry metadata to change this page.

Default base severity: **high**. Final risk also records known size/FK modifiers.

Ordinary index builds block writes; concurrent builds have explicit transaction and partition restrictions.

## Required evidence

- Index name, ordinary relation kind, simple columns and observed index metadata agree.
- Concurrent requests retain explicit transaction context and partition-parent facts.

## Conditional alternative

Consider CREATE INDEX CONCURRENTLY for a supported ordinary table outside an explicit transaction. It has multiple phases, lock waits and possible invalid-index cleanup. For partitioned parents, review supported leaf-build/attach procedures; this is not universally lock-free.

## Boundaries and limitations

- CONCURRENTLY cannot run in an explicit transaction or directly on a partitioned parent.
- Concurrent builds have multiple phases, lock waits and possible invalid-index cleanup.
- Expression, opclass, storage and conditional variants outside the supported binding are incomplete.
- Registry severity is the rule default; condition-specific findings can use another base severity.
- Policy severity and confidence are distinct; unknown evidence is explicit.
- Confirmed operation effects require matching PostgreSQL 13/15/16 evidence.
- No calibrated duration or general safety guarantee is available.
