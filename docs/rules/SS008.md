# SS008: CHECK or foreign key validation requested

Generated by `make docs` from the public registry; edit registry metadata to change this page.

Default base severity: **high**. Final risk also records known size/FK modifiers.

Immediate validation can scan existing rows while adding an eligible CHECK/FK constraint.

## Required evidence

- Named CHECK/FK definitions, captured validation facts and supported requested SQL agree.
- Immediate addition and later validation have distinct scan/lock stages.
- Confirmed constraint effects require a supported ordinary relation; partition/inheritance variants remain uncertain.
- Revalidating a retained already-valid constraint does not establish a new scan.

## Conditional alternative

For eligible CHECK/FK only, consider ADD CONSTRAINT ... NOT VALID, then VALIDATE CONSTRAINT separately. Both stages still acquire locks and NOT VALID enforces new writes. This is not an alternative for UNIQUE, PRIMARY KEY or NOT NULL.

## Boundaries and limitations

- NOT VALID is eligible for CHECK/FK, not UNIQUE, PRIMARY KEY or NOT NULL.
- NOT VALID retains addition locks and new-write enforcement; validation can fail on existing rows.
- FK validation also acquires ROW SHARE on the referenced relation; the finding lock describes the source table.
- Registry severity is the rule default; condition-specific findings can use another base severity.
- Policy severity and confidence are distinct; unknown evidence is explicit.
- Confirmed operation effects require matching PostgreSQL 13/15/16 evidence.
- No calibrated duration or general safety guarantee is available.
