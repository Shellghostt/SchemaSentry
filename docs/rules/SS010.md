# SS010: Enum membership removed or renamed

Generated by `make docs` from the public registry; edit registry metadata to change this page.

Default base severity: **critical**. Final risk also records known size/FK modifiers.

Known removed enum membership or type identity can invalidate stored/application values; an exact rename remains an application compatibility change.

## Required evidence

- Both versioned catalogs contain known ordered enum labels; omission is unknown.
- Supported rename/recreation requests bind to observed membership and column references.

## Conditional alternative

Coordinate application readers and inspect dependent objects. PostgreSQL has no direct DROP VALUE; a replacement type/rebuild requires an explicit value mapping and migration plan. Label rename is supported but can affect string consumers.

## Boundaries and limitations

- Added labels alone are not removal; a supported label rename has high base policy risk.
- PostgreSQL has no direct DROP VALUE; rebuild/data mapping remains a conditional manual plan.
- Domain/composite wrappers and references outside captured scope are explicit dependency gaps.
- Captured columns do not describe all application string consumers or uncaptured schemas.
- Registry severity is the rule default; condition-specific findings can use another base severity.
- Policy severity and confidence are distinct; unknown evidence is explicit.
- Confirmed operation effects require matching PostgreSQL 13/15/16 evidence.
- No calibrated duration or general safety guarantee is available.
